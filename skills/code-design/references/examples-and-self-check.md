# 案例与自检

这些案例校准决策，不强制所有项目采用相同结构。

## A：视频保存揉进页面

请求：整理保存功能职责，行为不变。

先追踪允许保存、选择水印、视频处理、相册写入和状态展示。明确规则及请求生命周期归属，再把不同变化原因的责任落到项目已有位置。

合理：页面展示状态；保存流程拥有政策与次序；处理和存储提供机制；取消与晚到结果有归属。普通函数/服务即可，不必每步新建接口。

不合理：没读链路就生成十几个空转发对象；页面与处理器分别判断水印；提取后遗漏资源释放。

## B：两个相似校验

请求：两个验证函数相似，是否抽公共函数？

注册与历史导入的允许范围、错误文案和演进原因可能不同。核对共享的是同一知识还是偶然相似代码。

合理：只提取稳定底层判断，政策各自拥有；或保留少量重复并解释原因。相似外形不能独立证明违反 DRY。

## C：多种计费方式

请求：客户采用不同计费方式，未来继续增加。

先明确金额单位、舍入、输入与结果契约。算法可作为策略，业务入口选择；简短算法可用函数映射，无需每种一个类。

验证共同契约与边界金额，账务兼容需确认历史规则版本。不把客户身份硬编码为算法，不用开闭原则隐藏政策版本变化。

## D：异步覆盖最新选择

请求：先点 A 再点 B，A 晚返回导致界面退回。

按时间追踪事件、请求及用户意图归属。使用已有机制中的请求身份、版本或取消等最小方案，阻止过期结果写入，覆盖失败和销毁清理。

存在多个状态不自动需要状态模式。验证返回顺序互换、取消和销毁；仅复杂转换本身难维护时考虑状态模式。

## E：只读审查/只改文案

请求：只检查职责问题先别改；或只改按钮文字。

前者提供证据与建议，不修改业务代码；后者完成文案与必要检查，不重构组件。范围外实质问题可简要指出，不自动扩大任务。

## F：接口实现不等价

请求：把两个存储实现统一到一个接口。

核对不存在对象、失败、覆盖、一致性和生命周期。一个实现不支持删除，不能抛未实现异常却声称可完全替换。按调用需求分能力或明确可选能力契约，检查已知调用方。

## 使用后的自检

- 是否先证明问题，再选原则和模式？
- 简单函数能做的事，是否扩成多层类与接口？
- 方案/审查是否误改代码？
- 重构是否意外改变错误、时序、资源或公共契约？
- 是否把名称、行数、存在 if 当作缺陷证据？
- 是否强制所有语言面向对象、所有项目采用相同层数？
- 测试是否验证实际结果，还是仅验证新类被调用？
- 报告是否区分事实、风险、建议与未验证部分？

文件格式校验只证明结构可加载，不证明每次决策正确。案例是行为检查材料；未实际执行的独立评测不得写成已通过。
