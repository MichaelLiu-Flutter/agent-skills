# 目标与原则：把口号变成判断

## 设计目标

目标存在取舍，不要求每个模块都达到相同程度。优先保证正确性和既有契约，再根据需求选择可维护性、性能、扩展性等重点。

| 目标 | 可观察证据 | 常见误判 |
|---|---|---|
| 正确可靠 | 状态转换合法，失败可处理，重要操作不重复、不丢失 | 编译成功就是正确 |
| 职责明确 | 规则有明确归属，变化原因对应相关模块 | 每个类只有一个方法 |
| 高内聚 | 同一职责的数据与操作靠近，常一起变化的逻辑集中 | 同类型文件放一起就是内聚 |
| 低耦合 | 依赖必要契约，不依赖无关内部细节；改动传播可控 | 文件互不导入才算低耦合 |
| 易读 | 名称表达业务意图，主要流程直接，跳转适量 | 函数越短越好 |
| 易改 | 一条规则变化只影响有限且合理的位置 | 所有代码预留扩展点 |
| 可测试 | 能验证业务结果与边界，依赖可合理控制 | 每个类配一个 mock |
| 可观测 | 失败能定位到过程与边界，必要日志关联同次操作 | 每行打印日志 |
| 性能适当 | 有目标与测量，资源和调用次数可控 | 缓存一定更快 |
| 一致性 | 同类问题沿用项目已验证的命名、契约和机制 | 所有功能套一样的目录 |

## SOLID 的正确用法

### S：单一职责原则

一个模块围绕一个主要责任及相关变化原因。用谁提出什么变化、会导致修改这里来检查；无需僵硬地只认一个利益相关者。

异常信号：界面变化、计费规则、网络协议和磁盘保存都迫使同一对象修改；多个地方分别决定同一条规则。先分离决策与机制，保留清楚的协调入口。

不应拆：同一职责所需的校验、计算和结果组装；拆开后只能互相转发且没有独立语义的步骤。

### O：开闭原则

在已经明确且反复发生的变化方向上，提供稳定扩展点，减少对既有核心逻辑的修改。

异常信号：每增加同类实现，就要修改多个不相关模块的类型判断。可考虑策略、注册或多态，但局部条件分支不自动构成问题。

不应做：为未知变化抽象；认为旧代码永远不能改；为了消除一个 switch 增加框架。变化维度不稳定时，直接修改通常更清楚。

### L：里氏替换原则

调用方通过共同契约使用不同实现时，各实现应满足契约，不意外加强前置条件、削弱后置条件或破坏状态不变量。

检查合法输入范围、结果语义、错误行为、同步/异步约定、取消与资源生命周期。类型兼容只是必要条件之一。

一种实现不支持关键操作时，优先划分能力接口或改用组合；不要到处检查具体类型，也不要把真实失败伪装成空成功。

### I：接口隔离原则

让调用方依赖自己需要的能力。按使用场景和语义边界划分接口，不按方法数机械切片。

异常信号：实现被迫填写无意义方法；只读调用方必须依赖写入能力；无关能力变化影响大量调用方。

避免每个方法一个接口，或把总是一起使用且生命周期一致的能力过度拆分。

### D：依赖倒置原则

需要保持稳定的业务策略，不直接绑定频繁变化的外部细节；在确有必要的边界上让细节实现业务需要的契约。

接口表达调用方需要的能力，不能只是复制 SDK 的所有方法。依赖注入是提供依赖的办法，不自动实现依赖倒置；增加接口也不自动改善依赖方向。

具体实现稳定、简单且无隔离需求时，直接依赖可以合理。用现有架构说明选择，避免接口和实现之间的纯形式分离。

## 其他常用原则

| 原则 | 执行判断 | 使用边界 |
|---|---|---|
| KISS，保持简单 | 选择满足行为和约束、理解成本最低的方案 | 不用简单掩盖遗漏的错误或并发处理 |
| YAGNI，暂不实现未需要的能力 | 没有当前需求、契约或演进证据，就不预建框架 | 已知迁移、法规、公共协议属于真实需求 |
| DRY，知识不重复 | 同一规则或权威事实尽量只有一个维护来源 | 文本相似但变化原因不同，可以保留重复 |
| 关注点分离 | 隔离不同规则、机制和生命周期的变化 | 协调流程本身也是职责 |
| 信息隐藏 | 用稳定入口表达能力，保护内部状态和不变量 | 不用无意义 getter/setter 假装封装 |
| 最少知识原则 | 少依赖其他对象内部关系，减少跨层链式访问 | 查询/遍历天然访问结构时，不机械加转发 |
| 组合优于继承 | 能力复用和可替换行为优先考虑组合 | 稳定的“是一个”关系且满足替换契约时，继承合理 |
| 显式依赖 | 看得出依赖和副作用来源，能控制生命周期 | 不要求所有值传过多层参数 |
| 状态权威唯一 | 同一事实有明确权威来源，派生值可计算或可追踪同步 | 缓存/快照需说明失效和一致性 |
| 契约清楚 | 成功、失败、空结果、部分成功含义明确 | 不强制所有异常统一成一种错误 |

## 状态与资源也是职责

涉及异步、并发、订阅或外部资源时，回答：

- 谁创建、更新、销毁？责任能否成对追踪？
- 状态是权威事实、派生值还是缓存？何时失效？
- 旧请求晚于新请求返回，哪次结果有效？页面/任务销毁后怎么办？
- 临时失败、取消、重试、部分成功是什么？重试会否重复副作用？
- 事件表达已发生事实，还是命令请求执行？顺序和交付保证是什么？

仅检查当前任务涉及的边界。不要为同步纯函数添加无用途的取消、重试或事件系统。
