# 工作流程与验证

## 1. 建立任务边界

确认方案、审查或修改；找出允许变化的行为、文件/模块、公共协议与已有工作区改动，不覆盖别人的修改。读取项目规则与设计方式，不把参考架构当作迁移目标。

定义验收：什么输入/操作应得到什么结果，哪些旧行为必须保持。审查任务的验收是能否证实问题、影响和建议。

## 2. 沿真实链路理解

入口 → 流程与业务决策 → 数据与外部能力 → 结果/错误反馈。按任务裁剪，不扫描全仓。

复杂链路可列出：

| 对象/模块 | 核心职责与变化原因 | 输入/输出 | 状态与资源所有权 | 依赖及契约 |
|---|---|---|---|---|
| 实际对象 | 具体业务描述 | 空/失败语义 | 权威状态、释放者 | 调用方需要什么 |

检查测试中的行为事实，以及实现有无隐藏假设。图和文档是线索，关键判断绑定当前源码或执行证据。

## 3. 诊断与取舍

每个实质问题说明触发条件 → 当前行为/修改传播 → 后果 → 证据。

- **已证实缺陷**：存在违反当前契约/需求的路径。
- **设计风险**：存在具体变化或失败场景，但未证明已发生。
- **可选改进**：主要改善阅读或一致性，不夸大成故障。

比较保持现状/最小修改与增加边界/采用模式。有真实取舍才列多个方案，不为流程生成空泛选项。

收益看重复规则、改动范围、外部隔离、状态/资源保护；成本看新增概念、跳转、生命周期、间接调用、迁移与兼容负担。

## 4. 落地边界

先确定谁拥有决策、协调次序、执行机制，再确定接口与文件落点。独立业务政策不放通用工具库，通用机制不由各页面重复实现。

优先现有组合入口，不在业务代码到处查全局容器。公共接口变化检查所有已知调用方、实现方、序列化/数据库格式和兼容要求。

结构重构尽可能与行为变化分开；需一起变化时分别说明和验证。大迁移可分阶段保留兼容入口，切换顺序可验证；不长期维护两套同一规则。

## 5. 边界检查：仅选相关项

| 边界 | 核查内容 |
|---|---|
| 输入/数据 | 空值、范围、单位、共享可变数据、格式兼容 |
| 错误 | 业务拒绝、系统失败、取消、部分成功；不吞错伪造成功 |
| 异步/状态 | 旧结果覆盖新意图、销毁后的回调、重复操作、不变量 |
| 并发 | 原子性、共享同步、锁顺序、跨实例/进程范围 |
| 资源 | 连接、句柄、流、监听、任务创建与释放成对 |
| 事务/重试 | 原子操作范围、幂等依据、失败状态与恢复 |
| 安全 | 已涉及的信任边界、权限归属、日志敏感信息 |
| 性能 | 实测热点、重复查询/遍历、失效、数据规模与背压 |

模式本身不保证这些正确。需要某处幂等，不代表应新增通用重试框架。

## 6. 按风险验证

- 规则/算法：边界输入、已知结果、不变量；必要时属性测试。
- 多实现/适配器：共同契约与各自失败路径。
- 状态/异步：操作顺序、晚到结果、取消、销毁、重复触发与终态。
- 数据/集成：必要集成测试，事务、序列化与错误映射。
- 公共接口：编译/类型检查已知调用方与实现方，验证兼容路径。
- 界面：适用的组件或实际交互验证，单元测试不替代设备/浏览器证据。
- 低影响无行为变化：适当静态检查与人工确认，不增加镜像实现的测试。

先跑受影响检查；通过后仅因新证据、修改或未解决风险扩大验证。失败先判断是否本次引入，不谎称既有失败通过，不删有效断言。

## 7. 收尾复核

看最终 diff，排除无关格式化、依赖升级、迁移。删除代码先核查引用、动态注册和兼容入口。项目要求认知/文档维护时，最终稳定后按其流程执行。

审查输出证据，方案输出职责、取舍与步骤，实现输出修改和实际验证。明确未覆盖部分，不使用满足全部原则作为验收结论。
